## architect

- [architect/design] Django support matrix is 4.2, 5.2, 6.0, 6.1 across Python 3.10–3.13, per-series legal combinations only — why: verified on djangoproject.com 2026-09-15 that the currently supported series are 5.2 LTS / 6.0 / 6.1 and that 4.2 reached end of extended support in April 2026, while spec §3 fixes 4.2 as the floor; 4.2 is kept as a best-effort CI-tested target and documented as such — alternatives: drop 4.2 (contradicts the spec), add Python 3.14 (spec caps at 3.13).
- [architect/design] Python×Django combinations restricted to what Django itself supports (4.2 → 3.10–3.12; 5.2 → 3.10–3.13; 6.0/6.1 → 3.12–3.13) — why: the install FAQ pins these and an impossible cell would fail CI for no reason — alternatives: a full cross product with skips.
- [architect/commands] Lint is `uv run ruff check . && uv run ruff format --check . && uv run python -m django check --settings=tests.settings && uv run python -m django makemigrations admin_errors --check --dry-run --settings=tests.settings` — why: ruff is the style gate, `django check` exercises our own system checks W001–W003/E001–E002, and `makemigrations --check` fails the build on a model change without a migration; `python -m django` keeps every segment a plain `uv` invocation — alternatives: `make lint` (extra indirection the intake explicitly removed), ruff alone (misses the two Django gates).
- [architect/commands] e2e up/down are `make e2e-up` / `make e2e-down`, e2e itself is `uv run --extra e2e pytest e2e -q` — why: up needs several steps plus backgrounding and a readiness poll, which a single chained command cannot express; `make` is a standard toolchain binary, and keeping playwright in its own `e2e` extra keeps the per-phase `uv run pytest -q` loop lean — alternatives: a project shell script (refused by the orchestrator), putting pytest-playwright in the `dev` extra (slows every phase's install).
- [architect/commands] `make e2e-up` exits 0 with a message when `demo/manage.py` does not exist and when port 8000 already answers — why: the intake requires idempotency, and Phases 0–3 have no user-facing surface so the e2e step must be a free no-op there rather than a failure — alternatives: pinning `-` for e2e until Phase 4 (would need the orchestrator's state edited mid-run).
- [architect/commands] e2e server runs `runserver 127.0.0.1:8000 --noreload` with its pid in `.autodev/e2e-server.pid`; ready URL `http://127.0.0.1:8000/admin/login/` — why: `--noreload` gives one pid to kill, so no step can leave a listening process behind; the ready URL is fixed by the intake — alternatives: gunicorn (a new dependency for the demo alone).
- [architect/adr] Eight ADRs written: project-DB storage via the ORM, background writer thread, fingerprint as a frozen contract, versioned JSON payload, admin-only UI, four-mechanism bounded storage, `view_issue_context` permission, zero-dependency src-layout packaging — why: each is expensive to reverse because it is load-bearing on stored data, on the public API, or on the dependency promise — alternatives: folding bounded storage into the storage ADR (it has its own settings contract and eviction semantics), an ADR for the version matrix (cheap enough to change, so it lives in ARCHITECTURE.md → Constraints instead).
- [architect/profile] `.autodev/PROFILE.md` was rewritten from "Django + htmx site" to "reusable Django app (library)" and the htmx section deleted outright — why: there is no `config/` project, no `apps/<app>/` tree, no services/selectors split and no htmx here; ADR 0005 makes the UI admin templates plus ≤ 3 KiB of vanilla JS, and htmx would be the only runtime dependency beyond Django — alternatives: adapting the htmx guidance (would leave false guidance later sessions trust).
- [architect/nfr] Assumed non-functional numbers where the spec is silent: capture p99 ≤ 8 ms without locals; count-only capture p50 ≤ 0.3 ms; guard-rejected capture p50 ≤ 50 µs; `store_batch` query budgets ≤ 3 / ≤ 7 / ≤ 8 per aggregate; admin list ≤ 12 queries and p95 ≤ 300 ms at 5 000 issues; admin detail ≤ 15 queries; ≥ 5 000 enqueues/s; up to 32 worker processes; `ready()` ≤ 5 ms; writer queue ≈ 64 MiB worst case — why: the guide requires numbers rather than adjectives, and these are the values the tests will pin as upper bounds — alternatives: leaving them unstated (nothing to assert against).
- [architect/design] The e2e suite covers the spec §13 manual QA script only, not a second copy of `test_admin.py` — why: browser tests are the slowest and most fragile layer and are the likeliest thing to hang an unattended run; permission and query-count assertions belong in the Django test client — alternatives: broad browser coverage of every admin case.
- [architect/design] `EmailNotifier` sets `notified_at` with a conditional UPDATE *before* sending, and a failed send is not retried — why: setting it after would let two workers double-send, and a retry queue on the error path is exactly the failure mode the design forbids; an operator who missed one email still sees the issue in the admin — alternatives: set-after (double-sends), retry with backoff (unbounded work in the writer thread).
- [architect/design] Request **method and path** are readable with `view_issue` alone; everything else in the request block needs `view_issue_context` — why: a traceback without knowing which endpoint produced it is much less useful, and a path carries far less personal data than headers, cookies, POST bodies or the user block — alternatives: gating the whole request block (hurts the common triage case), gating nothing (defeats ADR 0007).
- [architect/scope] No pytest-playwright, no Makefile, no project files were created at this step — why: the architect step produces design documents only; Phase 0 owns the scaffold and is bound by the Makefile contract written into PROFILE.md — alternatives: scaffolding now (out of this step's scope).
- [orchestrator/architect] lint_command set to `uv run ruff check . && uv run ruff format --check . && uv run python -m django check --settings=tests.settings && uv run python -m django makemigrations admin_errors --check --dry-run --settings=tests.settings` by this session (was `(none)`)
- [orchestrator/architect] e2e_command set to `uv run --extra e2e pytest e2e -q` by this session (was `(none)`)
- [orchestrator/architect] e2e_up_command set to `make e2e-up` by this session (was `(none)`)
- [orchestrator/architect] e2e_down_command set to `make e2e-down` by this session (was `(none)`)

## roadmap


- [roadmap/phases] Roadmap is 10 phases; spec §15's Phase 1 is split into `settings-models-fingerprint` and `capture-and-storage`, and spec's Phase 6 into `demo-project` and `docs-and-release` — why: spec Phase 1 alone is 13 modules plus 4 test modules and spec Phase 6 mixes a whole Django project with the release checklist; each of the four resulting phases fits one focused session of ≤ 15 tasks — alternatives: keeping the spec's 7 phases verbatim (two of them would not fit a session and would land half-done at 03:00).
- [roadmap/phases] `demo-project` (Phase 7) comes **before** `admin-ui` (Phase 8), inverting spec §15 where the demo is last — why: the intake fixes the e2e/browser surface as the demo project and turns the browser pass on from the admin-UI phase, and `make e2e-up` (PROFILE contract) runs `demo_seed` before starting the server, so the demo must exist before the first real browser pass; the demo's URLs only exercise capture, which is complete after Phase 5 — alternatives: a throwaway minimal demo in the admin-UI phase and the real one later (two demos to maintain), or no browser pass until the last phase (risk #1 would stay open until the run is nearly over).
- [roadmap/phases] A dedicated `postgres-pass` phase (Phase 6) sits between retention and the demo — why: the intake makes SQLite the per-phase gate and requires a PostgreSQL pass no later than immediately after spec Phase 3, and risk #5 wants it while `storage.py` is still fresh; a phase of its own means a PG failure does not block SQLite phases — alternatives: folding it into the retention phase (it would be skipped if that phase ran long), waiting for the release phase (a late rework of `storage.py`, exactly what risk #5 predicts).
- [roadmap/phases] `demo/docker-compose.yml` (postgres:16) is created in the `postgres-pass` phase, ahead of the rest of `demo/` — why: the PG pass needs a reproducible server and PROFILE.md fixes that compose file as its only location; `make e2e-up` already exits 0 when `demo/manage.py` is absent, so a lone compose file in `demo/` breaks nothing — alternatives: testing against the local Postgres.app `psql` 17.4 only (not reproducible in CI), moving the compose file to the repo root (contradicts PROFILE.md).
- [roadmap/test] `test_command` confirmed unchanged as `uv run pytest -q` from the repository root with no venv activated — why: fixed by the intake as the orchestrator's gate; Phase 1 owns making it true via the `dev` extra plus `DJANGO_SETTINGS_MODULE = tests.settings` in `[tool.pytest.ini_options]` — alternatives: `make test` (the intake explicitly removed that indirection), adding `--cov-fail-under` to the gate (coverage belongs in CI, not in the per-phase loop).
- [roadmap/ci] Coverage `--cov-fail-under=90` is enforced in the CI workflow from Phase 1 but is **not** part of `uv run pytest -q` — why: spec §18 requires ≥ 90 % for `src/admin_errors` and risk #16 warns it will otherwise be gamed; keeping it out of the per-phase gate stops a coverage dip from masquerading as a functional failure while still failing the branch — alternatives: coverage in the phase gate (slower loop, confusing failures), coverage only in the last phase (gaps discovered too late to fix cheaply).
- [roadmap/scaffold] Phase 1's "trivial passing e2e case" is a browser-free spec in `e2e/` (harness import plus a server-reachability fixture that skips when nothing is listening) — why: the end-to-end command must be green from Phase 1 on a clean checkout, and there is no server before Phase 7; an `xfail` or a skipped-only suite would violate the no-loosened-tests rule — alternatives: no `e2e/` directory until Phase 8 (the e2e command would fail rather than no-op).
- [roadmap/version] `__version__` starts at `0.1.0.dev0` and is bumped to `0.1.0` in the final phase together with the CHANGELOG promotion and the migration squash — why: keeps every intermediate wheel distinguishable from the release and makes the release step one explicit edit — alternatives: `0.1.0` from Phase 1 (nine phases of wheels claiming to be the release).
- [roadmap/scope] Publishing to PyPI stays out of scope for this run; the release phase ends at `python -m build` + `twine check` + a clean-venv wheel install — why: fixed by the intake clarifications — alternatives: uploading to TestPyPI (needs credentials no one can supply tonight).
- [roadmap/i18n] Ukrainian is the only shipped locale catalogue, added in Phase 9 with the i18n markup — why: spec §12.4 names `locale/uk/LC_MESSAGES` specifically; marking strings and translating them in one phase avoids a second pass over every template — alternatives: i18n markup in Phase 8 with the catalogue later (every template touched twice).

## p01-plan

- [p01-plan/packaging] The `package` tox env and CI job run `django-admin check` + `migrate` against a new dependency-free `tests/package_settings.py` instead of spec §14.1's "demo settings" — why: `demo/` does not exist until Phase 7, so pointing the job at demo settings would leave it red for six phases and teach the run to ignore the one check that proves the wheel is complete (risk #17); the module is pytest-free so it imports in a clean venv holding only the wheel + Django — alternatives: skip the package job until Phase 7 (risk #17 stays unverified), create a stub `demo/` now (Phase 7's scope, two demos to reconcile).
- [p01-plan/toolchain] `tox-uv` is added to the `dev` extra and `tox.ini` uses `runner = uv-venv-runner` — why: PROFILE.md assumes `uv` provides and downloads the 3.10–3.12 interpreters for the matrix (only 3.13 is a system Python on this machine) and plain tox cannot do that; it is a dev-only tool, so the zero-runtime-dependency promise is untouched — alternatives: plain tox plus manually installed pythons (not reproducible, and the orchestrator cannot install interpreters), nox (a second runner for no gain).
- [p01-plan/ci] `.github/workflows/ci.yml` delegates every job to a `tox` env and only *lists* the 11 Python×Django cells in `matrix.include` — why: the matrix then has exactly one source of truth (`tox.ini`), so a local `uv run tox` and CI cannot drift, while the acceptance criterion that ci.yml enumerates the cells is still met literally — alternatives: duplicating the pip install commands in the workflow (two matrices to keep in sync), a reusable workflow (indirection for five jobs).
- [p01-plan/pytest] `[tool.pytest.ini_options]` sets `testpaths = ["tests"]` and `pythonpath = ["."]` — why: the per-phase gate `uv run pytest -q` must not collect `e2e/`, which needs the separate `e2e` extra, and `pythonpath` makes `tests.settings` importable with no venv activated and no `PYTHONPATH` export; the e2e command passes its path explicitly — alternatives: a second `pytest.ini` inside `e2e/` (two configs), `--ignore=e2e` in `addopts` (breaks the explicit e2e invocation).
- [p01-plan/coverage] `--cov-fail-under=90` is passed in the CI invocation only, never in `addopts` — why: the roadmap and risk #16 want the branch to fail on a coverage dip without a coverage dip masquerading as a functional failure in the per-phase gate — alternatives: coverage in `addopts` (every phase's gate turns red for the wrong reason), coverage only in the last phase (gaps found too late).
- [p01-plan/scaffold] `src/admin_errors/migrations/__init__.py` is created empty in Phase 1 and `AdminErrorsConfig.default_auto_field = "django.db.models.BigAutoField"` is set now — why: `makemigrations admin_errors --check --dry-run` is part of the lint command from this phase and needs a stable target, and fixing the auto field before Phase 2 generates the one shipped migration avoids a follow-up field migration (risk #19) — alternatives: let Phase 2 create both (first lint run would exercise an app with no migrations module).
- [p01-plan/e2e] The Phase 1 e2e suite is one unconditionally passing harness-contract case plus one case gated on a `server_available` fixture that skips when nothing listens on `http://127.0.0.1:8000/admin/login/` — why: `uv run --extra e2e pytest e2e -q` must be green from Phase 1 with no demo project, and an all-skipped suite or an `xfail` would be a loosened check; the gated case runs for real from Phase 7 without being rewritten — alternatives: no `e2e/` directory until Phase 8 (the e2e command would fail rather than no-op), an `xfail` marker (forbidden).
- [p01-plan/tox] The `celery` tox env runs the full suite with the `celery` extra installed in Phase 1 rather than spec §14.1's `tests/test_celery.py` only — why: that file does not exist until Phase 5 and pytest exits 5 on an empty selection, whereas running the whole suite with celery present is a real check today (the guarded import must not break when celery is importable); Phase 5 narrows the command — alternatives: an empty placeholder `tests/test_celery.py` (a test that asserts nothing), dropping the env until Phase 5 (a missing matrix cell in CI).
- [p01-plan/makefile] `make demo` / `make demo-pg` are placeholders that print that `demo/` arrives in Phase 7 and exit 0 — why: PROFILE.md fixes the target names now but the demo project is Phase 7 scope, and a target that explains itself cannot be mistaken for a working demo; no acceptance criterion in this phase covers them — alternatives: omitting the targets (breaks the documented Makefile contract), exiting non-zero (a red target for six phases).

## p01-implement

- [p01-implement/ci] `ci.yml` triggers on `push` to `main` and `autodev/**` (not every branch) plus `pull_request`/`workflow_dispatch` — why: this run works on `autodev/spec-*` branches and a wildcard push trigger avoids editing the workflow again for a differently-named branch — alternatives: `branches: ["**"]` (fires on throwaway branches too).
- [p01-implement/tox] `tox.ini` `package` env uses `package = skip` + a manual `uv venv`/`uv pip install` of the built wheel into `.tox/package-install`, rather than tox's normal `deps =`-based install, because tox has no built-in "install this run's freshly built wheel by glob" primitive — why: keeps the packaging proof (wheel installs standalone, `django check`/`migrate` pass against `tests.package_settings`) without a second packaging tool — alternatives: `deps = dist/*.whl` (tox resolves deps before `build` runs, so the glob would match a stale or missing wheel), a custom script file (against the "no shell scripts, Makefile owns multi-step logic" pattern already set for `e2e-up`).
- [p01-implement/makefile] Fixed a Makefile bug found during T11 verification: the original `e2e-up` split the "no demo/" guard and the rest of the recipe into two separate `@`-prefixed recipe lines; under GNU make 3.81 (no `.ONESHELL`) each recipe line is its own subshell, so `exit 0` in the guard only ended that one line and make fell through to `uv run python demo/manage.py migrate …`, which failed because `demo/` doesn't exist yet. Fix: merged the guard into the same backslash-continued shell as the rest of the recipe so `exit 0` there ends the whole target. Verified: `make e2e-up` now prints the skip message and exits 0 (was exit 2 with a `python3: can't open file 'demo/manage.py'` error before the fix) — why: T11's verification table caught it; the plan's design section did not call out the one-recipe-line requirement explicitly — alternatives: none, this is a correctness bug in the plan's own contract, not a design choice.
- [p01-implement/tests] Added `tests/__init__.py` and `e2e/__init__.py` (not listed as separate plan artifacts) — why: `tests.settings` / `tests.package_settings` / `e2e.conftest` are imported as dotted packages (from `tests/test_scaffold.py` and `e2e/test_harness.py`), which needs `tests/` and `e2e/` to be real packages under `pythonpath = ["."]` — alternatives: namespace packages (works on the Python versions here but is a less explicit contract for a `src`-layout project that already treats `admin_errors` as a regular package).


## p01-review_fix1

- [p01-review_fix1/blocker1] Moved the `dev` tool set from `[project.optional-dependencies]` to `[dependency-groups] dev` in pyproject.toml, and every `extras = dev` in tox.ini became `dependency_groups = dev` — why: `uv run` only auto-installs the default dependency group, not optional extras, so `uv run tox`/`uv run pytest -q` failed with `Failed to spawn: tox` on a clean checkout (proven: `UV_PROJECT_ENVIRONMENT=$(mktemp -d)/venv uv run tox --version` → error); dependency groups are installed automatically — alternatives: add `uv sync --all-extras` before every CI step (five extra steps, easy to forget on a new job), `uv run --extra dev tox …` (same duplication, still breaks bare `uv run pytest -q` from the acceptance criterion).
- [p01-review_fix1/blocker2] Split the generic `[testenv:py{310,311,312,313}-dj52-{sqlite,postgres}]` / `dj61-{sqlite,postgres}]` sections into `-sqlite`-only sections, and gave `py313-dj52-postgres` / `py313-dj61-postgres` their own explicit sections with `extras = postgres`, `set_env DJANGO_DB=postgres`, `pass_env ADMIN_ERRORS_TEST_PG_URL` — why: tox 4 uses the first section whose expanded name matches, so the generic brace section was silently winning over the dedicated postgres section and the CI `postgres` job ran SQLite and reported green (proven with `tox c -e py313-dj52-postgres` before/after the fix) — alternatives: reorder sections (undocumented, fragile to future edits), a single section with conditional `set_env` (tox has no per-cell conditionals inside one section name).
- [p01-review_fix1/major1] Fixed `tox -e package`'s wheel install: replaced the literal `dist/*.whl` argument (tox runs commands with no shell, so the glob was never expanded — `uv pip install` failed with "invalid wheel filename") with `uv pip install --find-links dist django-admin-errors 'Django>=4.2'`. Running the env end to end then surfaced a second, previously-masked bug: `.tox/package-install/bin/python` (the freshly built venv's interpreter) was never reachable because it wasn't in `allowlist_externals`, so `django check`/`migrate` failed with "not allowed, use allowlist_externals to allow it". Added `.tox/package-install/bin/python` to `allowlist_externals`. Verified `uv run tox -e package` exits 0 end to end (build, twine check, wheel install, `django check`, `migrate`) — why: risk #17 (packaging completeness) had zero working coverage before this — alternatives for the glob: `package = wheel` at the `[testenv]` level (installs whatever tox last built, not necessarily this run's fresh wheel, and conflicts with `package = editable` used by every other env); for the allowlist: `{toxinidir}/.tox/package-install/bin/python` (tried first — tox's allowlist match did not accept the `{toxinidir}`-prefixed absolute form here, so the plain relative path is used, matching how the command itself is already written).
- [p01-review_fix1/major2] Added `tests/test_toolchain.py`: stdlib-only (`configparser` + `re`) tests that pin `tox.ini`'s `env_list` to the exact 11-cell PROFILE matrix + lint/postgres/celery/package, assert no `{sqlite,postgres}` shadowing pattern survives, assert both postgres envs carry `DJANGO_DB=postgres`/`extras=postgres`, assert the package env never references a literal `dist/*.whl`, and scrape `ci.yml`'s `matrix.include` (regex, no PyYAML) plus its five job names against the same 11 cells — why: acceptance criterion 7 had no executable proof and all three defects above were invisible to a human reading the files — alternatives: add PyYAML to the `dev` group to parse ci.yml exactly (a new dependency for one test file; the regex is precise enough for this fixed, hand-written block), shell out to `tox c --json` in the test (slower, couples the test to tox's CLI availability at test time rather than the static files).
- [p01-review_fix1/minor1] `database_from_url` now `unquote()`s the username and the path-derived database name, not just the password, and `tests/test_scaffold.py` gained `test_database_from_url_unquotes_username_and_database_name` with a percent-encoded username and database name — why: `urlsplit().username`/`.path` are percent-encoded exactly like `.password`, so a DSN like `postgres://svc%40tenant:pw@h:5432/db` previously produced a `USER` Postgres would reject — alternatives: none, this was a plain omission.

## p02-plan

- [p02-plan/conf] `conf.settings` caches the merged dict and clears it on **every** `setting_changed` signal, not only when `setting == "ADMIN_ERRORS"` — why: the signal fires only under `override_settings`/`modify_settings`, the reset is a single dict assignment, and this also covers `DEBUG`/`BASE_DIR`/`DATABASES` overrides that later phases read through the same proxy, so no future key can be stale — alternatives: filter on the setting name (one more place to update when a phase starts reading a new Django setting), no cache at all (rebuilds the 38-key dict on every attribute access on the capture hot path).
- [p02-plan/conf] Attribute access for a name not in `DEFAULTS` raises `AttributeError`, while an unknown key *in the host's dict* is kept in the merged view and only reported by `W001` — why: our own typos must fail loudly at import/first use, but a host typo must never crash a host that merely has a stale settings key — alternatives: raise on unknown host keys (turns a warning-level misconfiguration into a hard startup failure), return `None` for unknown attributes (silently disables features when we typo a key).
- [p02-plan/conf] `IN_APP_INCLUDE` stays `None` in the proxy; the "default to `settings.BASE_DIR` if defined" resolution of spec §5 is deferred to `context.py` in Phase 3 — why: only in-app frame detection consumes it, the resolution is filesystem-shaped behaviour rather than a setting value, and keeping the proxy a dumb dict view makes `as_dict()` exactly the documented table — alternatives: resolve it inside `conf` (the proxy would report a default that spec §5 does not list, and `as_dict()` would stop matching the docs).
- [p02-plan/conf] Mutable defaults (`IGNORE_LOGGERS`, `IGNORE_EXCEPTIONS`, `IN_APP_EXCLUDE`, `NOTIFY_ON`) are shared list objects documented as "do not mutate", not deep-copied per read — why: matches how `django.conf.settings` itself behaves, and a per-read copy would allocate on the capture path for a hazard nothing in the codebase triggers — alternatives: `deepcopy` on every read (allocation on a hot path), tuples in `DEFAULTS` (the type would differ from what a host supplies, so `IGNORE_LOGGERS` would be a tuple by default and a list when overridden).
- [p02-plan/checks] `E002` reads `sqlite3.sqlite_version_info` from the stdlib module at call time and never opens a database connection; it is skipped when the configured `DATABASE` alias is absent from `DATABASES` (that case is `E001`, Phase 3) — why: system checks must not connect to the database, and reading the module attribute at call time is what makes the criterion's "patched SQLite version" test possible — alternatives: `connections[alias].Database.sqlite_version_info` (couples the check to Django backend internals and is harder to patch), running a `select sqlite_version()` query (a DB round trip inside a check).
- [p02-plan/checks] Checks are registered by explicit `register(fn, Tags.compatibility)` calls inside `AppConfig.ready()` (with a local import of `admin_errors.checks`), not by a module-level `@register` decorator — why: the roadmap deliverable says "registered from `AppConfig.ready()`", and it keeps importing `admin_errors.checks` free of global side effects for tests that call the check functions directly — alternatives: decorator at module level (registration would happen on any import, including a test importing the module for a direct call, making double registration order-dependent).
