# Risk register — django-admin-errors

Ordered by expected cost (likelihood × impact). Written at the architect step, 2026-09-15.
"Where it is handled" names the phase and the module or test that owns the mitigation.

| # | Risk | Likelihood | Impact | Mitigation | Where it is handled |
|---|---|---|---|---|---|
| 1 | **We build the wrong product: the operator cannot actually triage from this UI.** Sampling means the event you want may not be stored; four limiters mean "my error is missing" has several causes; the grouping may merge or split wrongly. The result looks finished and is useless in practice. | Medium | Very high — the whole run is wasted | The §13 manual QA script is run end-to-end as an acceptance gate, by a human path (browser pass), not only by unit tests: three `/boom/` hits → one issue with count 3; `/storm/?n=5000` → < 1 s and ≤ 5 events; resolve → hit again → *regressed* badge + console email; dark mode readable. `errors_test` and `errors_stats` exist specifically so a confused operator can self-diagnose, and the README FAQ maps each silent failure to an instrument. | Phase 4 (browser pass), Phase 6 (`test_demo.py`, manual QA script, README FAQ) |
| 2 | **Secret or PII leak through a stored payload or an ungated template.** Payloads carry production headers, cookies, POST bodies and frame locals. A missed `perms.admin_errors.view_issue_context` gate on one include, or one payload field rendered outside a gate, exposes production data to any staff user with `view_issue`. | Medium | Very high — this is the compliance promise the product is sold on | Scrubbing is delegated to Django's own `get_exception_reporter_filter(request)`, so `@sensitive_variables`, `@sensitive_post_parameters` and the host's filter all apply (never hand-rolled). Gating is enforced in the view **and** the template, including the "Copy as text" traceback. Each permission is tested in isolation asserting the sensitive strings are *absent* from the response body. Settings and environment are never stored (spec §16). | Phase 1 (`context.py`, `test_context.py`), Phase 4 (`admin.py`, templates, `test_admin.py` permission cases), ADR 0007 |
| 3 | **Capture raises, recurses, or hangs and takes the host down.** The pipeline runs on an already-failing request. A raising `__repr__`, a host `BEFORE_SEND` that throws, an exception inside our own storage, or an unloaded `request.user` each turns an ordinary 500 into a broken worker or an infinite loop. | Medium | Very high — we become the outage | Whole pipeline wrapped in `try/except BaseException` with `KeyboardInterrupt`/`SystemExit` re-raised. Thread-local recursion guard, permanently set on the writer thread. Safe `repr()` catching everything with an `<unrepresentable …>` fallback. `BEFORE_SEND` and every signal receiver individually wrapped. No I/O and no shared lock on the synchronous path; `enqueue` is `put_nowait`. Explicit tests: exception raised inside a monkeypatched `storage` does not recurse or raise; `__repr__` raising produces the fallback; `request.user` raising does not break capture. | Phase 1 (`capture.py`, `test_capture.py` recursion case), Phase 2 (writer guard), ADR 0002 |
| 4 | **SQLite write-lock contention.** The default install adds a second writer to a database Django already writes to. `database is locked` under load means dropped errors — or, worse, blocked host requests if anything is done synchronously. | High on SQLite hosts | High | Structural: no DB access on the request path at all (ADR 0002); the writer holds its own connection; transactions are one-aggregate-small; retention deletes in chunks of 1 000. Behavioural: one retry after 100 ms on `OperationalError`, then drop the batch; never re-enqueue. Documented: WAL, `OPTIONS={"timeout": 20}`, and the dedicated-alias pattern as the real fix for SQLite hosts. | Phase 2 (`writer.py` retry), Phase 3 (`routers.py`, chunked deletes), Phase 6 (README SQLite tips) |
| 5 | **PostgreSQL-only defects land late.** The gate between phases is SQLite (intake); PG gets one dedicated pass. The savepoint rule around racing creates and the aborted-transaction behaviour after `IntegrityError` have no SQLite equivalent, so a bug there is invisible until that pass — after most of the storage code is written. | Medium-high | High — a late rework of `storage.py` | Code written before the pass must already honour spec §16: every racing create inside its own `atomic()` savepoint, no `select_for_update` anywhere. The PG pass is scheduled no later than immediately after Phase 3, while `storage.py` is still fresh, and is repeated before the run ends. The concurrency test (two threads, same new fingerprint, `transaction=True`) is the specific probe. | Phase 1–2 (write to the rule), dedicated PG pass after Phase 3, `test_storage.py` race case |
| 6 | **Thread-transport tests are flaky.** `TestCase` wraps each test in a transaction invisible to other connections, and the in-memory SQLite test DB behaves specially across threads. Flaky tests in CI erode the whole suite's authority and cost hours of re-running at night. | High | Medium-high | Default transport in tests is `sync`; thread tests opt in explicitly and use `transaction=True`. If a thread test is flaky on SQLite, switch that test to a file-based test DB via `TEST["NAME"]` (spec §16) — never by adding a sleep and never by skipping. The `sink` is injectable, so most writer tests need no database at all. | Phase 2 (`test_writer.py`), guide rule: no skipped or loosened tests |
| 7 | **Grouping is wrong in practice.** Over-merge (quoted-literal normalisation collapses distinct bugs) or under-merge (a message format normalisation misses) — the second one is worse, because it also triggers admission drops and evicts real issues. | Medium | Medium-high | The algorithm is pinned by golden-value tests and by targeted normalisation cases (numbers, UUIDs, hex, addresses, timestamps, quoted strings, whitespace) plus same-message-two-culprits and two-types-one-message. The `fingerprint=` override is the documented escape hatch, documented next to the over-merge rule. The demo's `/boom/<int:n>/` and `/keyerror/<slug>/` make both behaviours visible to a human. | Phase 1 (`test_fingerprint.py`), Phase 6 (demo URLs, README) |
| 8 | **Admin template incompatibility across Django 4.2 → 6.1.** We extend `admin/change_list.html` and `admin/change_form.html` and rely on admin CSS variables; block names and variables are only semi-public and have shifted between releases. | Medium | Medium | The matrix actually renders the pages (`test_admin.py`), it does not merely call the views, so a block rename fails in CI rather than in a user's browser. Only documented CSS variables are used, never hard-coded colours. A visual check in the demo in light and dark is a Phase 4 acceptance criterion. | Phase 4 (`test_admin.py` across the matrix, manual visual check), ADR 0005 |
| 9 | **N+1 queries in the issue list.** 50 rows × a 14-day sparkline is the obvious trap, and it appears as "the admin is slow" only once there is real data. | Medium | Medium | Sparkline data comes from a single `Prefetch` filtered to the last 14 days; the summary cards are three aggregate queries. `assertNumQueries` upper bounds on the list page (≤ 12) and the detail page (≤ 15), and on each `store_batch` path, on both backends. | Phase 4 (`test_admin.py`), Phase 1 (`test_storage.py` budgets) |
| 10 | **Django 4.2 is EOL upstream** (extended support ended April 2026) but the spec fixes it as the floor. Supporting it costs matrix slots and blocks use of anything newer; it also implies a security promise we cannot keep for Django itself. | Certain | Medium | Keep it — spec §3 is explicit and conservative deployments still run it. Documented in `ARCHITECTURE.md` → Constraints and in the README as best-effort: tested in CI, but Django's own security support is the host's responsibility. Python floor 3.10 follows from it. | Phase 0 (`pyproject.toml`, `tox.ini`, CI matrix), Phase 6 (README compatibility section) |
| 11 | **Fork / preload / autoreloader breaks the writer.** gunicorn `--preload` and uwsgi fork after import: the child inherits a `Writer` object whose thread does not exist, and silently records nothing. `runserver`'s two processes are the same class of bug. | Medium | High when it happens — total silent data loss in production | Lazy thread start on first `enqueue()`, never at import or in `ready()`. `os.getpid()` compared on every `enqueue()`; a mismatch discards inherited state and starts a fresh thread. Tested explicitly (`test_writer.py` pid-change case). Documented in the README's gunicorn/ASGI notes. | Phase 2 (`writer.py`), Phase 6 (README) |
| 12 | **Capture is silently disabled in the host.** `propagate: False` on `django.request`, `DEBUG` interactions, or a `CAPTURE_LEVEL` above what the host logs — each produces an app that installs, migrates and shows an empty list forever. | High | Medium — bad first impression, support burden | System check `W002` warns on the propagation trap; `W001` catches typo'd settings keys; `E001` catches a missing DB alias. `manage.py errors_test` pushes one error through the full pipeline and prints the admin URL. The `got_request_exception` marker receiver is a fallback for attaching the request. README FAQ item #11 covers exactly this. | Phase 1 (W001/E002), Phase 3 (W002, `errors_test`), Phase 6 (README FAQ) |
| 13 | **Email notifications go wrong**: duplicates from concurrent workers, or a slow SMTP server stalling the writer thread and therefore all error persistence. | Medium | Medium | Throttle via a conditional `UPDATE … WHERE notified_at IS NULL OR notified_at < threshold` — only the worker whose UPDATE touched a row sends; tested with two threads. Notifier runs from an `on_commit` hook so the row is durable first, and its exceptions are swallowed. README recommends a queued email backend in production and documents replacing Django's `mail_admins` handler (which mails on *every* occurrence); check `W003` flags that overlap. | Phase 5 (`notifications.py`, `test_notifications.py`), Phase 6 (README) |
| 14 | **e2e/browser layer costs more than it returns.** Playwright needs a browser binary, a running server and a seeded database; it no-ops for Phases 0–3 and is the most likely thing to hang an unattended night run. | Medium | Medium — lost hours, not lost correctness | `make e2e-up` is idempotent and exits 0 with a message when `demo/` does not exist yet, so Phases 0–3 cost nothing. It runs `migrate` and `demo_seed` first, backgrounds the server, waits for `http://127.0.0.1:8000/admin/login/`, and writes a pid file that `make e2e-down` uses. Browser install is a one-time idempotent step inside `e2e-up`. The e2e suite stays small: the flows from spec §13's manual QA script, not a second copy of `test_admin.py`. | Phase 4 onward (`e2e/`, Makefile targets), `.autodev/PROFILE.md` |
| 15 | **Scope creep into non-goals.** Tracing, breadcrumbs, a REST API, Slack notifiers and multi-tenancy all look cheap next to what is already built, and each would be a large unbudgeted cost. | Medium | Medium | Spec §2 is the explicit boundary and the roadmap does not contain them. The signals (`issue_created`, `issue_regressed`, `issue_status_changed`) are the sanctioned extension point and are the answer to every "could it also…" request. | All phases; ARCHITECTURE.md → Rejected alternatives |
| 16 | **Coverage ≥ 90 % is gamed rather than met**, or the suite is loosened to go green at 02:00 with nobody watching. | Medium | Medium | No `# pragma: no cover` on capture or storage paths (spec §18). No deleted, skipped, `xfail`-ed or loosened tests and no disabled lint rules — a red suite is fixed in the product. Coverage is enforced in CI, not merely reported. | All phases; CI config in Phase 0 |
| 17 | **A packaging defect ships**: templates, static files or locale catalogues missing from the wheel, so the app installs and then fails to render. | Low-medium | High for a release, zero for this run (no upload) | `src/` layout means tests import the installed package. The `package` CI job builds, runs `twine check`, installs the wheel into a clean venv and runs `django-admin check` + `migrate` on a minimal project — which is what proves the non-Python files are present. | Phase 0 (job exists), Phase 6 (green as a DoD item), ADR 0008 |
| 18 | **Unbounded growth despite the limiters** — a combination of settings or a bug in retention lets the host's database grow without bound. | Low | Very high if it happens — we damage a production system | Four independent mechanisms, each cutting a different dimension (ADR 0006), so one failing does not remove the ceiling. Each retention rule is tested in isolation with a frozen clock; eviction order and hysteresis are tested; `errors_stats` reports actual numbers; the worst-case bound is computed and documented in the README. | Phase 3 (`retention.py`, `test_retention.py`), Phase 6 (README storage bound) |
| 19 | **Migration churn.** Several development migrations ship instead of one, making the first install harder to review and pinning mistakes into other people's databases. | Low | Medium | Squash to exactly one initial migration before release (spec §16); `makemigrations --check --dry-run` is part of the lint command, so a model change without a migration fails the build. | Phase 0 (lint command), Phase 6 (squash before 0.1.0) |
| 20 | **Unattended run stalls on an environment problem** — Docker/Postgres unavailable for the PG pass, or a hung server from a previous e2e step holding port 8000. | Medium | Low-medium — lost time, recoverable | Docker and `psql` were both verified present at the architect step. The PG pass is a dedicated, isolated step whose failure does not block SQLite phases. `make e2e-up` is idempotent about an already-listening port and `make e2e-down` always runs. No step leaves a background process behind. | `.autodev/PROFILE.md`, Makefile targets, orchestrator step boundaries |
