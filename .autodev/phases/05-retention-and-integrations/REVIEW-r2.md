## [MINOR] Eviction regression test does not pin the chunking — it passes against the pre-fix code
`tests/test_retention.py`

`test_eviction_chunks_past_the_sql_variable_limit` creates 2500 issues with `MAX_ISSUES=100` and asserts only the end state (`evicted_issues == 2400`, `Issue.objects.count() == 90`). The pre-fix `_evict_status` produced exactly that same end state: I ran its single-list form verbatim on this branch — 2410 ids in one `pk__in`, SQLite 3.53.1 — and it returned `(2410, {'admin_errors.Issue': 2410})` leaving 90 rows, no error, because 2410 is far below the 32766 parameter limit. Reproducing the original `OperationalError: too many SQL variables` needs ~33k issues on this SQLite and 65k+ on PostgreSQL, which no test should have to create. So the test documents the fix but does not protect it: a revert to the unbounded id list stays green on SQLite >= 3.32 and on PostgreSQL, and only breaks on an old SQLite (999 params, still allowed by E002) or at production scale — exactly the condition rule 6 exists for.

**Fix:** Assert the invariant instead of the end state: wrap the `run_cleanup()` call in `connections[alias].execute_wrapper(...)` (or a `django_assert_num_queries` context inspecting `connection.queries`) that records `len(params)` per statement, and assert the maximum is `<= retention.CHUNK_SIZE`. That fails immediately on any reintroduced unbounded `pk__in`, on every backend, with 2500 rows. A cheaper alternative is `monkeypatch.setattr(retention, "CHUNK_SIZE", 100)` plus an assertion on the query count (which scales with the number of passes and so distinguishes one giant delete from many small ones).

## [NIT] Dedicated-alias test passes with or without the router, because storage writes with an explicit `.using()`
`tests/test_routers.py`

`test_capture_writes_only_to_the_dedicated_alias` installs `DATABASE_ROUTERS` but `storage.store_batch` already writes with an explicit `.using(conf.DATABASE)`, and every assertion in the test is an explicit `.using("errors")` / `.using("default")` query. Nothing in the test would change if `DATABASE_ROUTERS` were dropped, so it proves the `DATABASE` setting routes writes, not that `AdminErrorsRouter` does. The router's real job — making unqualified ORM access (what Phase 8's admin will do) hit the dedicated alias — is only covered by the unit tests on `db_for_read`/`db_for_write`.

**Fix:** Add one unqualified assertion inside the `override_settings` block, e.g. `assert Issue.objects.count() == 1` and `assert Event.objects.count() == 1` (no `.using()`), which resolves through the router and would return 0 without it.
